How Switchboard works

Switchboard looks like an OpenAI API to your applications and like an MCP server to your agents. Every chat completion an app sends is stored as a request in an outbox. Agents connected over MCP claim requests, produce the assistant's reply, and Switchboard returns that reply to the app as a normal OpenAI response (streaming included). Nothing leaves this machine unless you expose it.

1 · App
calls POST /v1/chat/completions with an API key
2 · Switchboard
queues the request, links it to its conversation, waits
3 · Agent
claim_request → answer → complete_request

Python (openai)

from openai import OpenAI
client = OpenAI(base_url="{{.OpenAIURL}}", api_key="sk-sb-…")
stream = client.chat.completions.create(
    model="switchboard/auto",
    messages=[{"role": "user", "content": "Hello!"}],
    stream=True,
)
for chunk in stream:
    print(chunk.choices[0].delta.content or "", end="")

Supported endpoints

  • POST /v1/chat/completions — streaming and non-streaming, tools/tool_calls, response_format, all params forwarded to the agent.
  • POST /v1/completions — legacy prompt API, converted to a chat request.
  • GET /v1/models, GET /v1/models/{id} — advertised models plus anything an online channel declares.
  • GET /v1/requests/{id} — Switchboard extension: poll the state of a request you submitted.

Model names are free-form: a request for gpt-4o is served by any channel that declared gpt-4o, a matching glob, or *. Responses carry x-switchboard-request-id and x-switchboard-conversation-id headers so you can find them here.

Give the agent the serving loop
Use the MCP prompt serve, read resource switchboard://guide, or install the skill: switchboard skill install. The loop is: open_channel once → claim_request (wait 25s) → reply with stream_delta/complete_request → repeat.

MCP tools

open_channelRegister this agent instance (name, models, concurrency). Returns channel_id.
claim_requestLong-poll for the next request routed to the channel. Returns messages, params, deadline.
stream_deltaSend partial text/tool calls to the caller immediately; renews the lease.
complete_requestDeliver the final answer (content, tool_calls, finish_reason, usage).
fail_request / release_requestHand the request back (retryable) or fail it for the caller.
extend_lease · heartbeat · get_request · queue_status · list_channels · close_channelHousekeeping and visibility.

Reliability model

  • Durable outbox. Requests live in SQLite; a claim is an atomic update. Nothing is lost if an agent disconnects.
  • Leases. A claimed request must see progress (stream_delta, extend_lease or completion) within the lease; otherwise it is returned to the queue for another agent, up to max attempts.
  • No duplicate output. Once an agent has streamed tokens to a caller, the request is never re-run by another agent; it fails instead.
  • Deadlines. Each request carries a timeout (per key or global). Callers get a 504 when it elapses; agents see the deadline in the claim.
  • Caller disconnects cancel the request so agents stop working on it.
  • Backpressure. Per-key rate limits (429), a maximum queue depth, and per-channel concurrency.

Reaching it from elsewhere

Switchboard binds to localhost by default. To let a hosted client (claude.ai, a phone, another machine) reach it, put it behind a tunnel or a TLS reverse proxy — e.g. cloudflared tunnel --url {{.BaseURL}}, ngrok http 8080, or Tailscale Serve — then set Public URL in Settings so OAuth metadata and MCP resource identifiers use the external address. The dashboard remains password-protected; API keys and agent tokens are unchanged.
